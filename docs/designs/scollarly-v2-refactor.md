## Problem Statement

The live app was built stage by stage as an engineer's console. The owner "got lost finding things": the admin/owner side has about 22 routes (leads, content, analytics, payments, team, audit, health, settings, security and more), no page explains itself, and the signed-in student side is 4 plain pages. Sign-in silently creates an account. There is no onboarding, no personalised student screen, no clear notification place, and the home page does not sell. The owner wants one refactor, with new `_2` source-of-truth files and exactly one stage in essentials_2.

## Demand Evidence (honest)

- Only the owner uses the app today. No real admin or student has used it.
- The one concrete pain, in the owner's words: "I got lost finding things."
- The owner's daily jobs are all four: work leads, update content, check money and results, manage team and system.
- The 7 features therefore come from the owner's own experience, not from watching users. Treat them as bets and test them (see The Assignment).

## Status Quo

Admin routes under `src/app/[locale]/(admin)/admin/*` (about 22 pages), student routes under `(student)/me` (4 pages), a public home at `/`, Google-only sign-in at `/sign-in`. Signed-in screens are a prerendered shell plus plain data functions in `src/server/edge/authed.ts` (ADR-040). The student has a local `progressSnapshot` for offline (`src/offline/progress-snapshot.ts`).

## Target Users

- **Owner and admins:** want one obvious place per job. Four tabs: Home, Leads, Content, Insights.
- **Student:** wants a clear next step and universities that match their course.
- **Parent:** applies for a child. Same role as a student (no 4th role). Child's details plus parent contact are collected.

## Constraints (unchanged, must be kept)

- CLAUDE.md rules: no push to main, feature branch and PR, only `server/repositories` imports Drizzle, only `server/auth` imports Neon Auth and otpauth, no access control in middleware (auth facade, `Actor`, row level security), no personal data in shells or caches, no admin libraries in public routes, no third-party scripts or hotlinked images, one WhatsApp helper, no physical deletes, no personal data in logs, UTC storage and WAT display, additive-first migrations, no paid service or hosting change, no unconfirmed stats, testimonials or bios.
- Workers Free: about 10 ms CPU per request. One screen = one data call. Public first load under 200 KB, public JavaScript under 118 KB gzip.
- Offline first: public reading, lead queue and student snapshot keep working. New screens go through translation keys (en live, fr ready).
- Low data: the splash is the OS launch screen plus a brief in-shell logo while loading. No timed or forced splash on the website (PRD removed it).

## Premises (agreed)

1. Features are bets from the owner's own use. The stage ends with a test where 3 real people use each flow.
2. Parent is a student-role account. The profile stores `relationship` from day one.
3. Onboarding creates a lead and needs a consent tick. The legal text (Q6, minors, student countries) stays an owner item.
4. Ordering is computed on the phone from public university data plus the saved answers. No personal data in any cached page. Works offline.
5. The landing page shows only confirmed facts until E1 to E3 are supplied. The hero course finder is a small script within the JavaScript ceiling.
6. Splash only on installed-app launch and shell load.
7. Admin offline snapshot holds totals only.
8. CRM: one dashboard per role. 4 number tiles, 1 main chart, 1 recent-activity list, week/month switch. Admin sees own results, owner sees everyone's. Few numbers, easy to read.
9. The round button is a "More" sheet with Notifications on top.
10. File names and carry-over as in D16.
11. Notifications are derived with one `notifications_seen_at` column.

## Cross-Model Perspective (Claude subagent, fresh context, no repo access)

- Steelman: turn an engineer's console into something three user types understand without training. The value is the lead pipeline.
- Most likely to break: "No account found" and onboarding-creates-lead on the 10 ms budget. A pre-check endpoint would let anyone test whether an email has an account. The onboarding write (answers, profile, lead, audit) must be one idempotent request that shares the offline lead queue's idempotency key.
- Likely wrong: a notifications table. Adopted: derived notifications (D11). Also adopted: `relationship` on the profile.
- Suggested build order: lead path first. Adopted as the module order. Not adopted: cutting the parent flow, charts, tours and admin offline totals, because the owner asked for them in the one stage.

## Recommended Approach: B, rebuild into hubs

### Sign-in and create-account (decision D3, premise: no pre-check)

- `/sign-in`: "Welcome back" with one Google button, and a clear link "New here? Create account".
- `/sign-up`: "Create your account" with one Google button and a choice "I am a student / I am a parent".
- After Google returns, the facade looks up `app_user`. Found: go to the role's home. Not found and came from Sign in: show "No account found for this Google account. Create one?" with Confirm and Back. Not found and came from Sign up: go to onboarding. **No `app_user` row is written until the person confirms or starts onboarding.** No endpoint ever answers "does this email exist" before Google.
- Existing sessions and the owner bootstrap rule (first verified sign-in of the configured email) are unchanged.

### Onboarding (student and parent)

- One screen per question (Image 1 style, sample only): Basics, School results, Study plan. Parent adds "Who is applying" (child's name, country) and the parent's name and WhatsApp.
- Progress bar, back button, "Saved on this phone" draft kept in IndexedDB (never sent until the last screen).
- Last screen: privacy and consent tick, then one idempotent write: profile answers, lead (same idempotency key and reference as the offline lead queue), audit row. Offline: queued like a lead, the student still sees their name and answers from the device.
- New data (additive): `student_profile` (user id, `relationship`, answers, `onboarded_at`, consent notice version, `notifications_seen_at`) with row level security (own row; staff read). A normalised **course list** is needed: today programmes have only `name` and `duration_months`. Add a `course_category` and `level` to each programme (additive column plus seed mapping) so "offering my course" is exact.
- Interrupted onboarding: reminder notification (derived from `onboarded_at` null).

### Personalised student experience

- Home: greeting with name, current stage, next step, "For you" shortlist.
- Universities tab: filter pre-selected from the chosen courses; those offering them first, then NAAC grade (A++ down to B), unknown last, ties A to Z. Computed client-side from the public universities data already cached by the service worker. The cached public page is identical for everyone.
- Only 4 of 9 seeded universities have a NAAC grade. Unknown grades sort last and are labelled "NAAC grade not stated" until the owner supplies them.

### Navigation (premise 9)

- One shared floating pill component (Image 3 shape, light colours) plus the round "More" button. Active tab highlighted. Labels visible. Keyboard and screen-reader support, safe-area padding, reduced motion respected.
- Admin and owner tabs: **Home** (dashboard), **Leads** (list, detail, link requests, data requests, SLA view as sections), **Content** (universities, FAQs, photos, blog, stale list as sections), **Insights** (funnel, sources, admin performance, payments). **More**: Notifications, Team, Security, Audit, Health, Settings, Profile, Sign out. Owner-only items hidden from admins.
- Old routes redirect to the matching hub section so bookmarks do not break. Each hub is one screen and one data call (CPU rule).

### CRM dashboards (Image 2 as sample, brand colours)

- Home per role: greeting and "what needs you today" (overdue leads, new leads, link requests), 4 tiles with a change versus the last period, one main chart, one recent-activity list, a week/month switch.
- Insights: the same numbers in more detail: funnel as progress bars, leads by country, performance per admin (owner) or own (admin), payments by month. Charts are small hand-built SVG, not a charting library, to protect the bundle and CPU. No chart without a one-line explanation.
- All times WAT. Numbers show "Last updated" when read offline.

### Notifications (D11, D12)

- A page under the round button, grouped Today / Earlier, each item with a one-tap action ("Open lead", "Message on WhatsApp"). The unread dot counts items newer than `notifications_seen_at`. "Mark all read" moves that time.
- Items are computed by the data function from existing rows (stage history, lead actions and SLA targets, link and data requests, payments, stale-content query, health checks, content published). No new table.

### Landing page (D1, D2, premise 5)

- `/` redesigned (Image 5 as sample): strong headline and one-line promise, course finder, 9 university logos, the 6-step process, FAQ teaser, install prompt, WhatsApp link. Self-hosted photos only (the four owner photos). No stats, testimonials or team until E1 to E3. Server-rendered, edge-cached, JavaScript only for the course finder.
- Course finder: pick a course (from the new course list), see the universities offering it (public data), CTA "Create your free account" carries the chosen course into onboarding.

### Brand assets (D15)

- Trace Image 4 to SVG (`public/brand/`). Generate icon set (192, 512, maskable, apple-touch, favicon) white on dark neon blue. Neon blue hex is an open item (current theme colour `#1d4ed8`). Update `manifest.ts` icons and background/theme colours. Installed-app splash and in-shell loading logo. Website keeps the black logo on white.

### Page help (D13)

- One shared `PageIntro` component (title and one-line purpose), shared empty-state component, one shared first-visit tour component with per-user "seen" flags (local storage plus `student_profile`/staff preference only, no personal data).

## Addendum, 2026-10-31: corrections found while writing the `_2` files

The approved text above is unchanged. These points were found by reading the code and are recorded in `system_architecture_2.md` (amendment log) for the owner to confirm:

1. "No `app_user` row until confirm" is not possible as worded: the session function creates the row at the first authenticated request. Version 2 keeps a pending row and adds `app_user.account_confirmed_at`. Nothing is a Scollarly account until the person confirms.
2. No new programme columns: `programme.field` (course category) and `programme.level` already exist and are empty; they are filled from the owner-approved list.
3. `notifications_seen_at` (and the tours-seen list) live on `app_user`, because staff have no student profile.
4. The student device copy holds a first name, extending the earlier "no name" rule.
5. Team, Audit log, Security, Settings and Health are all owner-only pages today, so an admin's More sheet holds only Notifications, Profile and Sign out; the owner's holds all of them (found in S13.1).
